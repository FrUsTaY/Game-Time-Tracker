# Отчет об ошибках и проблемах в GameTimeTracker

Этот документ содержит список обнаруженных багов, недоработок и архитектурных проблем в коде приложения.

## 1. Критический баг: Разные сохранения при автозапуске и ручном запуске
**Описание:**
При запуске приложения через автозагрузку Windows (через реестр) и при ручном запуске (двойным кликом по `.exe` файлу) создаются две разные базы данных, из-за чего пользователю кажется, что прогресс "сохраняется по-разному" или сбрасывается.

**Причина:**
В файле `app.py` используется относительный путь для базы данных:
```python
self.db = Database("data/gametracker.db")
```
При запуске из автозагрузки рабочей директорией (Current Working Directory) часто становится не папка с программой, а системная директория (например, `C:\Windows\System32`) или папка профиля. В результате папка `data` создается там. При ручном запуске рабочая директория — это папка с `.exe` файлом.

**Решение:**
Использовать абсолютный путь относительно расположения исполняемого файла.
Например, в `main.py` или `app.py` определять директорию через `sys.argv[0]` или `sys.executable` (для PyInstaller) и строить путь к БД от неё:
```python
import sys, os
base_dir = os.path.dirname(sys.executable if getattr(sys, 'frozen', False) else os.path.abspath(__file__))
db_path = os.path.join(base_dir, "data", "gametracker.db")
```

## 2. Гонка данных (Race Condition) при работе с SQLite
**Описание:**
База данных SQLite используется параллельно из двух разных потоков.
UI-поток (основной поток Tkinter) читает и пишет настройки, а фоновый поток `GameTracker` (созданный через `threading.Thread`) каждую секунду записывает данные о сессиях.
Хотя при инициализации стоит флаг `check_same_thread=False`, SQLite не поддерживает параллельную запись. Если оба потока попытаются сделать `INSERT` или `UPDATE` одновременно, приложение может упасть с ошибкой `sqlite3.OperationalError: database is locked`.

**Решение:**
Внедрить механизм блокировок (например, `threading.Lock`) вокруг всех операций записи в БД внутри класса `Database`, либо использовать очередь (`queue.Queue`) для передачи запросов на запись в один выделенный поток работы с БД.

## 3. Обновление GUI из фонового потока (Thread Safety Tkinter)
**Описание:**
В файле `tracker.py` вызывается коллбэк `self.on_tick(...)`, который напрямую привязан к методу `games_tab.update_tick` (вкладка интерфейса).
`_monitor_loop` работает в отдельном фоновом потоке, и, следовательно, этот поток напрямую изменяет элементы UI (через вызов `update_tick`).
Tkinter (и CustomTkinter) не является потокобезопасным (Thread-Safe). Обновление виджетов из стороннего потока может приводить к зависаниям, артефактам отрисовки или внезапным крашам (Access Violation) приложения.

**Решение:**
Передавать обновления в UI через метод `after()` или `event_generate()`.
```python
# Вместо прямого вызова UI:
# self.on_tick(...)
# Использовать метод главного окна:
window.after(0, lambda: games_tab.update_tick(...))
```

## 4. Проблемы производительности (I/O Bottleneck) в `GameTracker`
**Описание:**
В методе `_check_processes` в `tracker.py` внутри цикла каждую секунду для активной игры происходит чтение из базы данных:
```python
game = self.db.get_game_by_id(game_id)
saved_seconds = game['total_seconds'] if game else 0
```
Это создает избыточную нагрузку на диск и базу данных (один запрос к БД каждую секунду для каждой активной игры), что может вызывать микрофризы.

**Решение:**
Кэшировать значение `total_seconds` в памяти в словаре `self.active_sessions` при начале сессии и обновлять его локально. Записывать в БД только при окончании сессии (или раз в N минут для автосохранения).

## 5. "Зависшие" сессии (Ghost Sessions) при краше приложения
**Описание:**
Если приложение было завершено принудительно (через Диспетчер задач, или внезапным отключением питания), открытые игровые сессии в таблице `sessions` так и останутся с `ended_at = NULL`.
При следующем запуске программы эти сессии не очищаются и не закрываются, что может сломать статистику и графики.

**Решение:**
Добавить при запуске приложения (или при инициализации `Database`) очистку: проверять все незакрытые сессии и проставлять им `ended_at` равным текущему времени или времени `started_at + duration_seconds`.

## 6. Баг выхода через системный трей
**Описание:**
В `tray.py` в методе `_on_exit` вызывается `self.on_exit()`, что в свою очередь вызывает `sys.exit(0)` из контекста потока трея (pystray).
`sys.exit(0)` завершает только текущий поток (поток трея), а главный поток Tkinter (`mainloop`) может остаться висеть в памяти в виде процесса-зомби без окон.

**Решение:**
Для правильного завершения программы необходимо использовать методы главного потока. Из потока трея лучше вызывать `self.window.quit()`, чтобы корректно прервать `mainloop` Tkinter, после чего приложение закроется естественным образом.
